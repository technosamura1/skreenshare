# Проверка безопасности screenshare — 1 ноября 2026

Проверены исходники ветки `screenshare-pc`, сборка 0.13.0, транспорт UDP,
обмен кодами через ntfy, запуск дочерних процессов, загрузка DLL и журнал Defender.
Это целевая проверка и усиление защиты, а не независимый криптографический аудит.

## Исправлено в 0.13.0

* Раньше `BYE`, capabilities, ping, отчёты потерь и NAT-рукопожатие не имели
  криптографической проверки подлинности. Наблюдатель сети мог узнать токен из
  заголовка и подделывать команды. Теперь они передаются внутри AEAD-конверта
  ChaCha20-Poly1305; адрес собеседника выбирается после проверки подлинности.
* Повтор зафиксированной команды управления или сигнализации теперь отклоняется
  окном последовательностей после успешной проверки тега. Перестановка до 128
  последовательностей допускается. Обратное отражение своих команд отклоняется.
* Счётчик nonce управления расширен до 64 бит, направления разделены в nonce.
  При исчерпании счётчика или ошибке шифрования открытой отправки не происходит.
* Ключ мультимедиа друзей больше не зависит только от постоянного секрета пары
  и публичного 32-битного токена. Он также зависит от свежего 256-битного секрета
  кода хоста: повтор токена не приводит к повтору ключа/nonce между трансляциями.
* Старые коды хоста без секрета больше не принимаются. Пакеты без шифрования
  отклоняются после установки ключа. Во время трансляции проверяется адрес peer.
* GUI передаёт постоянный ключ друга через stdin дочернего процесса, а не через
  его командную строку. CLI-параметр `--media-key` оставлен для совместимости
  тестовых инструментов; вручную использовать его с настоящим секретом не следует.
* Раньше кеш FFmpeg принимался по совпадению размера DLL. Теперь проверяется
  SHA-256 содержимого относительно встроенного манифеста, включая файл, который
  записал параллельно запущенный процесс. Ошибка проверки останавливает запуск.
* DLL загружаются по абсолютному пути. Рабочая папка и PATH исключены из
  динамического поиска; системные DLL берутся из System32.

Протокол несовместим с 0.12.x: обновление требуется обоим участникам.

## Результаты проверок

* 252 теста прошли, 2 теста с обращением к настоящему серверу пропущены в обычном
  прогоне. Отдельные тесты покрывают подмену ключа/заголовка/тега, повторы,
  отражение команд, исчерпание счётчика, отсутствие открытой отправки при ошибке
  и подмену DLL файлом того же размера.
* `tools/security-smoke.py`: два локальных процесса без звука и записи. Проверены
  обычное и дружеское подключение через IPC, получение кадров (30 кадр/с в тесте),
  продолжение просмотра после поддельного открытого BYE и выход зрителя после
  настоящего STOP хоста. Это не проверка двух физических ПК через интернет.
* `cargo audit` 0.22.2: 355 зависимостей, 0 известных уязвимостей.
  База RustSec: `2295466c4e9df26647fd67d8fa1c705ac2fc7f81`, 30.10.2026.
  Предупреждение RUSTSEC-2026-0192: `ttf-parser` 0.25.1 не поддерживается.
  Нативные FFmpeg, Opus и драйвер ViGEm этим аудитом Rust не покрываются.

## Что остаётся ограничением

1. **Код друга — секрет доступа, а не публичное имя пользователя.** Он содержит
   постоянный симметричный ключ inbox. Его обладатель может читать адресованные
   этому inbox сообщения знакомства, включая ключевые материалы других друзей.
   Поэтому нельзя публиковать код или распространять его среди недоверенных лиц.
   Для безопасного публичного добавления нужны отдельные публичные ключи,
   подтверждение личности и обмен ключами для каждой пары; этого пока нет.
2. `identity.txt` и список друзей содержат ключи в открытом виде в профиле
   Windows. Защита зависит от учётной записи и прав файлов. Шифрование DPAPI
   и миграция существующих профилей пока не реализованы.
3. Прямой секретный код и ключ пары не обеспечивают forward secrecy.
   Компрометация ключей вместе с записанным обменом может раскрыть прошлые сеансы.
   Для следующего этапа нужен проверенный протокол с ephemeral DH/Noise/DTLS,
   а не дальнейшее расширение собственного рукопожатия.
4. Короткий код комнаты имеет 40 бит энтропии. PBKDF2 замедляет перебор,
   но не превращает его в 256-битный секрет и не является PAKE.
   Для чувствительного содержимого предпочтительнее длинный секретный код.
5. EXE не имеет Authenticode-подписи издателя. Подпись и стабильный выпуск
   помогут с доверием к происхождению, но не гарантируют отсутствие предупреждений.

## Windows Defender

В журнале найдены `Trojan:Win32/Bearfoos.A!ml` и `Bearfoos.B!ml` на версиях
0.12.9–0.12.16. По этим названиям нельзя доказать ложное срабатывание.
Точечная проверка EXE 0.12.19 с установленными сигнатурами 1.463.63.0 угроз
не обнаружила. Результат проверки 0.13.0 фиксируется в описании её релиза.

При проверке не добавлялись исключения, не отключалась защита и не восстанавливались
файлы из карантина. `MpCmdRun -Scan -ScanType 3 -File ... -DisableRemediation`
используется только как диагностический режим без удаления файлов; он игнорирует
исключения при этом сканировании. Не следует считать чистый локальный результат
гарантией того, что облачный Defender или SmartScreen на другом ПК не сработает.

Если обнаружение повторится, отправить конкретный EXE с SHA-256 в Microsoft
как разработчик: https://www.microsoft.com/en-us/wdsi/filesubmission
Никаких автоматических отправок бинарников или пользовательских профилей аудит не делал.
