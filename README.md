# screenshare

Показ экрана со звуком через интернет напрямую, без серверов и регистрации.
Видео — HEVC через NVENC (видеокарта NVIDIA, драйвер **471.41 или новее**), 60 кадров/с, ~40 Мбит/с. Если видеокарты NVIDIA нет
или драйвер старый — автоматически кодирует процессором (H.264, x264), см. «Если у показывающего нет NVENC».

## Как пользоваться

1. Запустите `screenshare.exe` — это один файл, ничего распаковывать не нужно. Если Windows спросит про доступ
   к сети — разрешите. (При первом запуске программа за секунду-две сама разложит FFmpeg в
   `%LOCALAPPDATA%\screenshare`.)
2. На первом экране две большие кнопки. Кто показывает — **«Показать экран»**: выберите карточку (весь экран, монитор или окно
   с живой миниатюрой) → «Начать показ». Появится код `H...` — «Скопировать код» и передайте зрителю.
3. Кто смотрит — **«Смотреть»**, вставляет код `H...` → «Смотреть». Появится код ответа `C...` — передайте его показывающему.
4. Показывающий вставляет код `C...` → «Подключить». У зрителя откроется ваш экран (можно на весь экран).
   **F11** или **двойной клик** — переключить полный экран / окно, **Esc** — выйти из полного экрана.

Все настройки (качество, звук, простое подключение, «Проверить на этом ПК») спрятаны под **«Дополнительно»** — по умолчанию
ничего настраивать не нужно.

### Что показывать: весь экран или одно окно

На странице «Показать мой экран» есть список **«Что показывать»**:

- **Весь экран** (по умолчанию) — основной монитор;
- **Монитор N** — каждый монитор отдельно (список появляется, если мониторов больше одного);
- **Окно: …** — любое открытое окно по заголовку. Зрители увидят *только* это окно, остальное (другие окна, рабочий стол,
  уведомления) в трансляцию не попадёт. Свёрнутые окна помечены «(свёрнуто)» — при старте такое окно будет
  развёрнуто, иначе у него нет картинки. Окно самой программы в списке не показывается.

Список окон обновляется каждый раз, когда вы открываете выпадающий список.

Как это работает для окна: захват через Windows Graphics Capture (нужна Windows 10 1903 или новее), курсор мыши
рисуется в картинке окна. **Разрешение трансляции не меняется** — оно равно разрешению основного монитора, а окно
вписывается в кадр по центру с чёрными полосами (маленькое окно увеличивается, большое уменьшается). При изменении размера
окна на лету картинка у зрителя подстраивается, а размер кадра остаётся тем же.

**Жёлтая рамка Windows вокруг окна.** Её рисует сама Windows, не программа (и она рисуется у вас на экране, в трансляции
её нет). Начиная с версии 0.6.2 программа просит Windows её не рисовать
(`GraphicsCaptureSession.IsBorderRequired = false`, только если такое свойство есть в системе). Что получится:
- **Windows 11:** рамки не будет, если включено «Параметры → Конфиденциальность и защита → Границы снимков экрана»
  → «Разрешить классическим приложениям отключать границу снимка экрана» (на чистой установке обычно уже включено; если
  рамка осталась — включите этот переключатель, при необходимости вместе с «Разрешить приложениям…» выше). Windows
  сама решает, послушаться ли просьбы; у программы без установочного пакета (наш exe) нет способа получить
  разрешение иначе, чем через эту настройку.
- **Windows 10 (включая 22H2):** такого переключателя в системе нет, **убрать рамку при показе одного окна нельзя**.
  Программа честно пишет об этом в статусе. Выход: показывать «Весь экран» — там захват другой (DXGI), рамки нет.
- Режим «вырезать окно из захвата экрана» (без рамки на любой Windows) **сознательно не сделан**: зритель увидел бы всё,
  что окажется поверх окна (чат, уведомления, пароли), а свёрнутое/перекрытое окно давало бы мусор — это ломает
  смысл «показываю только одно окно».

Других обводок программа не рисует: рамки вокруг предпросмотра и подсветки при наведении в её окне убраны.

Если выбранное окно закрыли или захват сломался (например, окно защищено от записи), программа **не останавливается**:
показывает весь экран и пишет красным в статусе, например «Окно «Блокнот» закрыто — показываю весь экран».
Если свернуть окно во время трансляции, зритель будет видеть последний кадр, пока окно не развернут обратно.
Звук не зависит от выбора: по-прежнему весь звук компьютера кроме Discord.

### Что именно сейчас видит зритель: окошко-предпросмотр

Пока идёт трансляция, в окне программы под статусом показано маленькое окошко (320×180, как «Вы демонстрируете экран» в
Discord) — **ровно те кадры, что уходят зрителю**: выбранное окно (с чёрными полями) или весь экран. Под ним подпись:
«Окно: <заголовок>» или «Весь экран». Если окно закрыли и программа перешла на весь экран, подпись становится красной
(«Окно ... закрыто — показываю весь экран»), а картинка — полноэкранной. Обновляется примерно 5–7 раз в секунду.

- **Дёшево и не влияет на трансляцию:** картинка уменьшается из того кадра, который уже подан кодеку (после его
  кодирования, в паузе между кадрами), сжимается и передаётся в окно в отдельном потоке. Если что-то не успевает —
  предпросмотр пропускает кадры, сама трансляция и задержка не страдают. На неподвижном экране он ничего не делает.
- **Свёрнутое окно программы — предпросмотр выключен:** пока оно скрыто или свёрнуто, картинки вообще не делаются
  (окно программы раз в ~1,5 с «даёт знать» хосту, что на него смотрят; перестало — хост замолкает через ~3,5 с).
  После разворачивания первая картинка появляется сразу.
- **Эффект «тоннеля» при показе всего экрана:** если показывать весь экран, а окно программы лежит на нём, зритель увидит и
  окно программы, а в нём предпросмотр, в котором уменьшенное окно программы с предпросмотром, и т. д. — с небольшой
  задержкой (это нормально, как зеркало в зеркале). Чтобы не было «тоннеля»: показывайте конкретное окно, либо
  окно программы держи на втором мониторе / свёрнутым (тогда предпросмотр и так выключен). Скрывать окно программы
  от захвата принудительно не стали: тогда зритель не увидел бы и его, а это может быть нужно.

**Предпросмотр можно выключить:** галочка «Показывать превью» под кнопкой «Остановить» (запоминается между запусками в
`%LOCALAPPDATA%\screenshare\gui.ini`). Выключено — никакой работы не делается вообще: хост не уменьшает кадры, не сжимает
и не пишет их в канал. Превью работает и в режиме «Проверить на этом ПК».

**«Проверить на этом ПК»** — трансляция и просмотр у себя же: вы увидите ровно то, что увидит зритель.

Коды одноразовые: на каждый запуск — новые.

### Простое подключение (beta): один короткий код

При «Показать мой экран» отметьте «Простое подключение (beta)» → программа покажет код вида `K7QM-X2PD`. Зритель вводит его в
«Смотреть» (туда же, куда раньше вставлялся длинный `H…`) — всё, ответ уходит сам. Под капотом те же коды
`H…`/`C…` пересылаются через публичный сервер ntfy.sh, но **зашифрованными** (ключ и имя «комнаты» получаются из короткого
кода, PBKDF2 150 000 раундов + ChaCha20-Poly1305): сервер видит только случайную строку и шифртекст. Код живёт 15 минут
(пока хост ждёт). Если не сработало — под кодом есть «Обычный способ» с длинными кодами, он работает как раньше.
Нужен `curl.exe` (есть в Windows 10 1803+ и 11). Свой сервер: переменная окружения `SCREENSHARE_RELAY=https://…` (ntfy).

## Если у зрителя лагает

Смотрите `%LOCALAPPDATA%\screenshare\viewer.log` (у зрителя; раз в 5 с одна строка) и заголовок окна просмотра
(«GPU · 58 к/с · декод 2.1 мс · пинг 40 мс»). В строке: какой декодер (видеокарта D3D11VA или процессор), время декода /
цвет+масштаб / показа (среднее/макс., мс), очередь кадров, сколько кадров пропущено («догоняя» и «переполнение»),
разброс времени прихода кадров и паузы >0,1 с (это сеть). Много «декод» → слабый процессор/нет GPU-декода; «паузы» и
«разброс» → интернет/Wi-Fi зрителя; «пропущено догоняя» → не успевает декодер. Качество — три кнопки (0.7.7):
«Авто» (по умолчанию), «Стандарт · 30 Мбит/с» и «Высокое качество · 60 Мбит/с». Два последних — потолок: при потерях программа сама снижает
битрейт. Если у зрителя лагает на «Стандарте» — смотрите журнал выше; пресетов ниже 30 больше нет (в командной строке
`--bitrate` по-прежнему любой).

## 0.7.4: треск в конце слов, 25–30 кадров/с вместо 50–60

Что нашли и поменяли (проверено только на симуляторе `tools/lossim` и сборке под wine; реальная сеть/NVENC/Windows — нет):
- **Звук — новый формат Opus (0x93).** 48 кГц стерео, 128 кбит/с, пакет 10 мс (раньше 2,5 мс), каждый пакет
  несёт ещё 2 предыдущих (потерять надо 3 подряд), отдельный запрос недостающих звуковых пакетов (ANACK) со своим сроком
  30–60 мс, потеря заделывается встроенной заделкой Opus. Раньше при потере 4–7% сети «заглушено» было 1400–2000 пакетов:
  потери идут пачками во время всплесков видео, а копия на один пакет назад пачку не переживает. Зритель сам сообщает хосту,
  что умеет Opus (пакет 0xA7); со старым зрителем хост шлёт прежний формат 0x92, новый зритель понимает оба.
  Буфер зрителя теперь 80–120 мс (было 40–100).
- **Сеть.** Пейсер видео: всплеск не больше 12 пакетов (было 48, это переполняло буферы роутеров — собственные потери),
  скорость отправки 1,6× битрейта (было 2×), дозапросы не больше 25% полосы. Стартовый битрейт 15 (было 20). Автоснижение
  битрейта теперь срабатывает и при устойчивых 4–5% потерь (не ниже 60% от выбранного). Если сеть отстаёт, хост пропускает
  кадр *до* кодирования, а не бросает уже закодированный (раньше это вызывало лавину запросов ключевого кадра).
- **Главная причина «хост шлёт 50, зритель показывает 25–30».** Звук задерживается в буфере, и чтобы звук и картинка
  совпадали, зритель держит каждый кадр столько же. При 60 кадр/с это 5–7 кадров в очереди — норма, но правило «догоняя»
  считало любую очередь ≥3 кадров отставанием и пропускало конвертацию двух из трёх кадров, хотя декод занимает 2 мс.
  Теперь кадр «опаздывает» только если он позже своего срока (приход + задержка звука) больше чем на 50 мс.
- **Конвертация цвета+масштаба (20+ мс на процессоре)** вынесена с потока декодера на 2 потока-конвертера (кадр копируется,
  ~1 мс); два кадра конвертируются параллельно, потолок вырос с ~45 до ~90 кадров/с. Если оба заняты, кадр пропускается и
  считается («конвертер занят»). Понижение до билинейного фильтра теперь с 14 мс (было 9). Перенос конвертации на видеокарту
  сделан в 0.7.5 (см. ниже).
- **В строке статуса зрителя** теперь: `N кадров/с показано (хост отправил A → дошло целиком B → декодировано C)` и
  `потери за 5 с: видео X% / звук Y%`; в диагностике — `картинка WxH → wxh` (размер видео и размер после вписывания в окно).
  Разница A→B — потери/сборка кадров в сети, B→C — переполнение очереди/ключевые кадры, C→N — «догоняя» и «конвертер занят».
  Хост в своей статистике пишет, сколько раз экран обновился за секунду (если ниже 60 — экран не рисует 60 кадров/с, например
  видео 24–50 кадров/с, и хосту нечего слать), сколько кадров отложено из-за сети и какой звук идёт (Opus/обычный).
  В `viewer.log` и на хосте пишутся размеры буферов сокета (просим 16 МБ приём / 8 МБ отправка).
- Команды проверки: `screenshare opustest` (кодек Opus работает), `screenshare convbench [--video-w --video-h --window-w --window-h]`
  (сколько мс занимает конвертация на этом компьютере).

## 0.11.1: драйвер геймпада внутри программы

Установщик драйвера **ViGEmBus 1.22.0** теперь встроен в `screenshare.exe` — скачивать ничего не нужно. Размер exe вырос
примерно на 6,3 МБ (с 12,9 до 19,2 МБ). Больше ничего не менялось (видео, звук, подбор качества, протокол и логика управления прежние).

- Страница «Показать», карточка «Удалённое управление», если включён геймпад и драйвер не найден: кнопка **«Установить драйвер геймпада»**.
  Программа распаковывает установщик в `%LOCALAPPDATA%\screenshare\vigembus`, запускает его с запросом разрешения Windows (UAC) и без окна
  (`/exenoui /qn /norestart`), ждёт окончания и сама перепроверяет, отвечает ли драйвер. Если тихая установка завершилась ошибкой —
  установщик запускается ещё раз с обычным окном. Рядом осталась маленькая кнопка «Страница драйвера» (ссылка на релиз автора).
- Итог показывается по-русски: «Драйвер геймпада установлен. Перезагрузка не нужна.» / «…Windows просит перезагрузку…» (код 3010 или
  драйвер ещё не отвечает) / «Установка отменена…» (отказ в запросе Windows) / «…ошибкой (код N)…».
- Скрытая команда `screenshare drvinstall` делает то же самое из консоли.
- **Не проверено на настоящей Windows:** сама установка (UAC, тихие ключи, перезагрузка, появление устройства, подпись драйвера на вашей
  версии Windows). Под wine проверено только то, что установщик распаковывается байт-в-байт (sha256 совпал); логика разбора кодов возврата
  покрыта юнит-тестами. Как проверить: ПК без ViGEmBus → «Показать» → галочка «Разрешить управление зрителю» → «Установить драйвер геймпада» →
  согласиться в окне Windows → дождаться сообщения; при просьбе перезагрузить — перезагрузиться и убедиться, что в карточке «Драйвер геймпада установлен»
  (или `joy.cpl` показывает «Xbox 360 Controller» при подключённом зрителе).
- Лицензия: ViGEmBus распространяется под BSD-3-Clause, разрешающей распространение в бинарном виде при сохранении текста лицензии —
  см. «Сторонние лицензии» ниже. Проект ViGEmBus закрыт автором в 2023 году (обновлений не будет), последняя версия 1.22.0 работает.
  Драйвер ставится в систему (Program Files) и остаётся после удаления screenshare; удалить его можно в «Приложения и возможности»
  («Nefarius Virtual Gamepad Emulation Bus Driver»).

## 0.11.0: удалённое управление (как Steam Remote Play / Parsec)

Зритель может играть на компьютере показывающего: свой геймпад (до 4), мышь и клавиатуру. Видео, звук, ratectl и кодировщик
не менялись; со старыми версиями (0.10.0 и ниже) всё работает как раньше — они просто не знают про управление
и игнорируют новые пакеты.

**Как это включить (по шагам).**
1. Показывающий ставит драйвер **ViGEmBus** (нужен только для геймпадов): на странице «Показать» кнопка «Установить драйвер»
   открывает https://github.com/nefarius/ViGEmBus/releases/latest. В 0.11.0 драйвер не был встроен (с 0.11.1 встроен, см. выше; установка с
   правами администратора, возможно, нужна перезагрузка). Без драйвера мышь и клавиатура работают, а геймпад — нет.
2. Показывающий на странице «Показать» ставит галочку **«Разрешить управление зрителю»** (по умолчанию выключена,
   с каждым новым показом сбрасывается) и при желании снимает «Геймпад» или «Мышь и клавиатура».
3. Зритель подключается как обычно. В панели поверх видео появляется кнопка с геймпадом, числом подключённых контроллеров и
   подписью «Управление». Если показывающий не разрешил управление, кнопка серая, а подсказка объясняет почему.
4. Зритель включает «Управление»: геймпады начинают передаваться (геймпад 1 зрителя → виртуальный геймпад 1 у показывающего,
   2 → 2 и так до четырёх), а клик по видео захватывает мышь (курсор прячется, движения идут как относительные).
5. У показывающего горит красная метка «Зритель управляет».

**Горячие клавиши.**
- Показывающий: **Ctrl+Alt+Shift+F12** — мгновенно отключить управление (всё отпускается, галочка снимается; чтобы вернуть,
  поставьте её снова). Работает, даже когда игра на весь экран.
- Зритель: освободить мышь — **Ctrl+Alt+Shift** или удерживать **Esc** секунду (короткий Esc уходит в игру); мышь
  освобождается также при потере фокуса окна, при отзыве управления и при выключении «Управления». **F2** — панель
  «Тест геймпада» поверх видео. Тот же тест есть в лаунчере: «Настройки → Тест геймпада» (кнопка «Проверить вибрацию»).

**Что делает программа.**
- Новые пакеты (`src/inputproto.rs`): `PT_INPUT 0xA8` зритель → показывающий, `PT_CTRL 0xA9` и `PT_RUMBLE 0xAA` назад;
  версия протокола управления в каждом пакете (=1), зритель сообщает о поддержке флагом `CAP_INPUT` в `PT_CAPS`.
  Пакет — снимок состояния, до ~100–200 байт: кнопки/триггеры/стики до 4 геймпадов, суммарные счётчики движения мыши и колеса
  (потерянный пакет только задерживает движение, курсор не «уезжает»), список зажатых клавиш и кнопок мыши и пронумерованные
  события нажатий/отпусканий, которые повторяются несколько раз (короткий тап не теряется, залипнуть нечему).
  Отправка при изменении (не чаще раза в 2 мс) и не реже раза в 100 мс; пакеты с устаревшим номером отбрасываются.
- Зритель (`src/inputview.rs`, `src/xinput.rs`): отдельный поток с повышенным приоритетом, опрос XInput 250 Гц (каждые 4 мс), отправка только при изменении и раз в 100 мс (через
  `xinput1_4.dll`, подгружается на лету), клавиши — по скан-кодам (раскладка не важна), мышь — сырые относительные движения.
- Показывающий (`src/inputhost.rs`): события применяются сразу в потоке приёма. Клавиатура и мышь — `SendInput`; геймпад —
  виртуальный Xbox 360 через ViGEmBus (крейт `vigem-client`); вибрация от игры пересылается зрителю и включает моторы его
  геймпада (`XInputSetState`), при тишине моторы гаснут сами.
- **Отпускание.** Всё (клавиши, кнопки мыши, виртуальные геймпады) отпускается: через ~1 с без пакетов, при отключении зрителя,
  при выключении галочки, по Ctrl+Alt+Shift+F12 и при закрытии показа.
- **Согласие.** Без галочки пакеты управления игнорируются, что бы зритель ни прислал; разрешены отдельно геймпад и
  мышь+клавиатура; принимаются пакеты только от подключённого зрителя с верным токеном. Разрешение передаётся зрителю
  (`PT_CTRL`), поэтому его интерфейс всегда показывает правду.

**Что важно знать.**
- Ввод попадает **во весь компьютер**, а не только в окно игры (как у Parsec): `SendInput` не умеет «в одно окно». Если показываете одно окно, зритель
  всё равно сможет двигать мышь и нажимать клавиши в других программах — разрешайте управление только тому, кому доверяете.
  Alt+Tab, Win и Alt+F4 зрителя в его системе не перехватываются; Ctrl+Alt+Del на показывающем недоступен для SendInput.
- Игры с античитом (EAC, BattlEye, Vanguard и др.) могут блокировать виртуальный ввод и виртуальные геймпады.
- Окна, запущенные от администратора, не принимают `SendInput` от обычной программы (UIPI): запустите screenshare тоже от
  администратора, если нужно управлять такой программой.
- Управление идёт по тому же обычному UDP без шифрования; токен подключения — общий секрет, а не защита. Видео и звук, как и
  раньше, тоже не шифруются. Не используйте это через недоверенную сеть.
- Курсор показывающего зритель видит в трансляции; задержку курсора определяет видеоканал, а не канал ввода.

**Проверено.** Сборка с `crt-static`, `tools/check-dlls.sh`, юнит-тесты (`cd tools/lossim && cargo test --release`):
кодек пакетов (границы, мусор, неизвестная версия), номера и избыточность, отпускание по таймауту и при отзыве,
запрет без разрешения и по устройствам, назначение слотов геймпадов, повтор и таймаут вибрации, а также тест по настоящему
UDP на 127.0.0.1 с потерями до 60 %, дублями и перестановками (зажатые клавиши и кнопки никогда не залипают, мышь не уезжает
при потерях до 40 %, виртуальный геймпад отключается через 1 с тишины, чужие и битые пакеты игнорируются). Лаунчер под wine со
скриншотами: карточка управления (драйвер найден и не найден, разрешено, отозвано аварийной клавишей), «Тест геймпада»
(с подставным геймпадом `SS_FAKE_PAD=1`), панель зрителя и окно «Тест геймпада» (`screenshare overlaytest`, скрытая команда для скриншотов).

**На настоящей Windows НЕ проверялось** (под wine нет ни драйвера ViGEmBus, ни геймпада, ни живого соединения):
работа XInput и вибрации, виртуальный геймпад в играх, `SendInput` в играх и окнах, захват мыши и сырой ввод, поведение при
масштабе системы 125–200 %, влияние античита, реальная задержка. Как проверить:
1. На показывающем установите ViGEmBus (кнопка «Установить драйвер»), перезагрузитесь, если попросит установщик.
   В карточке должно быть «Драйвер геймпада установлен».
2. Подключите геймпад на стороне зрителя. Откройте «Настройки → Тест геймпада»: стики и кнопки должны двигаться,
   «Проверить вибрацию» — включать моторы.
3. Показывающий: «Показать» → галочка «Разрешить управление зрителю» → «Начать показ». Зритель подключается.
4. Зритель: в панели видно число геймпадов; включите «Управление», нажмите F2 — панель покажет «геймпад 1 → виртуальный геймпад 1».
   У показывающего — «Зритель управляет» и «виртуальных геймпадов: 1».
5. Проверка геймпада на показывающем: `joy.cpl` («Параметры игровых устройств») или сайт gamepad-tester — должен быть «Xbox 360 Controller».
   Запустите игру с поддержкой геймпада. Мышь: кликните по видео, подвигайте; Esc 1 с или Ctrl+Alt+Shift отпускают мышь.
6. Нажмите Ctrl+Alt+Shift+F12 на показывающем: управление должно сразу отключиться, галочка сняться, виртуальный геймпад пропасть.
7. Закройте программу зрителя через Alt+F4 при зажатой клавише в игре: через ~1 с клавиша у показывающего должна отпуститься.

- **Экран соединения с шагами:** «Подготовка → Соединяемся → Проверяем канал → Идёт картинка» с крутящимся индикатором
  и подсказкой, если слишком долго. Шаги определяются по уже существующим сообщениям (протокол прежний). Ошибки — понятным
  русским текстом («Нет связи с сервером подключения», «Код устарел» и т. д.), исходный текст — в «Подробности»,
  кнопки «Повторить» и «На главную».

## 0.7.7: «Авто» качество, звук только из выбранного окна, лампочка сети

Проверено только на сборке, юнит-тестах (`tools/lossim`, 129 тестов, включая симулятор канала с узким горлышком) и запуске под
wine (окно программы, `--help`, Opus, `gputest`). На настоящей Windows, с живым захватом звука и реальной сетью — **не проверено**.
- **Качество «Авто» (по умолчанию).** Третья кнопка рядом со «Стандарт · 30» и «Высокое · 60». Хост стартует с 20 Мбит/с и каждые
  1,5 с поднимает ×1,25 до 60, пока у зрителя нет неисправленных потерь (`residual`/`gave_up`), пока не растёт пинг (RTT выше
  спокойного ×1,5 + 25 мс) и сырые потери не больше ~8%. При проблеме — шаг назад и остановка; дальше работает прежняя
  адаптация (срез при потерях, медленный возврат). Выбранная скорость показывается на экране трансляции («Авто: подбираю… сейчас
  N Мбит/с» → «Авто: выбрано N Мбит/с»). Ручные пресеты работают как раньше. В командной строке: `--auto-bitrate` (потолок
  `--bitrate`, по умолчанию 60). Зритель теперь присылает в отчёте и свой RTT (пятое поле; старые версии его просто игнорируют).
  Если пакеты «переставляются» (джиттер), сырые потери выглядят выше, чем есть — поэтому они почти не влияют на разгон.
- **Звук только из выбранного окна.** Флажок «Звук только из этого окна» (по умолчанию включён, виден когда выбрано окно).
  Используется захват звука процесса Windows (WASAPI process loopback, режим INCLUDE_TARGET_PROCESS_TREE) для PID окна (для
  UWP-приложений через ApplicationFrameHost ищется настоящий процесс — «по возможности»). Если не получилось запустить (старая
  Windows, нужна 10 build 20348+/11) — переходит на весь звук компьютера с пометкой в статусе. Режим «Весь экран» передаёт звук
  компьютера как раньше. Второй флажок «Не передавать звук Discord» — исключение Discord (EXCLUDE_TARGET_PROCESS_TREE); в режиме
  «Весь экран» без Discord исключается сама программа (чтобы звук просмотра не возвращался). Оба флажка можно менять во время
  показа (строка `AUDIO window=… voice=…` в stdin хоста); при смене окна/монитора захват звука перестраивается на лету,
  счётчик пакетов (временная шкала звука) продолжается — синхронизация с видео сохраняется. В момент смены источника звук может
  пропасть на ~0,1–0,3 с. Если процесс окна молчит — трансляция тоже тихая. Если показываете само окно Discord при включённом
  «только из окна», его звук будет передан. `--audio-all` и `--keep-voice` в командной строке.
- **Лампочка качества сети** у показывающего и у зрителя: зелёная «Сеть хорошая», жёлтая «Сеть слабая: снизил качество» (у
  зрителя «Сеть слабая»), красная «Сеть плохая». Считается по потерям, RTT, неисправленному ущербу, доле повторных отправок и
  срезу битрейта; с гистерезисом (хуже — через 1,5 с, критично — 1 с, лучше — через 6 с и на одну ступень). В подсказке при
  наведении — цифры. Пороги подобраны по расчёту и симулятору, на реальных сетях не калибровались.

## 0.7.5: цвет и масштаб на видеокарте (с автоматическим возвратом на процессор)

**Проверено только сборкой, симулятором `tools/lossim` и запуском под wine. Реальную видеокарту/Windows это не видело — первая
проверка у друга обязательна (см. «Как проверить»).**
- Раньше картинка после декодера D3D11VA копировалась в память и 20+ мс уходило на её перекраску NV12→BGR и масштаб на
  процессоре (2 потока). Теперь декодированная текстура (NV12/P010) сразу идёт в **D3D11 video processor** (`VideoProcessorBlt`),
  который переводит цвет и масштабирует под размер окна на видеокарте; читается назад уже готовая картинка размером с окно,
  и показ остаётся прежним (softbuffer), поэтому окно, полный экран, превью и скриншот-режим работают как раньше.
  Матрица цвета (601/709) и диапазон (limited/full) берутся из потока, как у процессорного пути.
- **Защита от чёрного экрана.** Любая ошибка при создании или работе видеопроцессора → навсегда переключаемся на процессор,
  кадр при этом не теряется (он читается назад обычным способом). Кроме того, на первых 2 кадрах после каждого (пере)создания
  (старт, смена размера окна/видео) та же картинка считается ещё и процессором и сравнивается (средняя разница на сетке
  ~64×48, допуск 28 из 255): чёрный экран или мусор от видеокарты → сразу показывается картинка процессора и GPU-путь
  выключается. Окно меньше 64 px и режимы с проверкой синхронизации звука/скриншотом идут через процессор.
- **Принудительно процессор:** флаг `screenshare.exe client --cpu-convert` либо переменная окружения
  `SS_CPU_CONVERT=1` (также `true/yes/on/да`).
- **Где видно, какой путь работает:** в строке диагностики зрителя `цвет+масштаб на: …` (видеокарта (D3D11 video processor) /
  процессор, 2 потока / …видеокарта отказала, переключился / …принудительно) и в `viewer.log` (при старте, при сверке первых
  кадров — с числом расхождения — и при переключении с причиной).
- **Как проверить без сети:** `screenshare.exe gputest [--video-w 1920 --video-h 1080 --window-w 1600 --window-h 900]` —
  создаёт на этой видеокарте устройство D3D11VA, кладёт на него тестовую картинку (цветные полосы + градиент), прогоняет
  ровно тот же код и печатает время GPU/процессора, расхождение и итог «ВИДЕОКАРТА ПОДХОДИТ» / «НЕ ПОДХОДИТ: причина»
  (в этом случае зритель сам работает на процессоре).
- **Не проверено:** успешный GPU-путь на реальном Windows (цвета, скорость, качество масштаба — драйверный билинейный фильтр
  может отличаться от бикубика swscale), полный клиент с реальным потоком NVENC, ресайз/полный экран. Чтение готовой картинки
  назад синхронное (поток декодера ждёт видеокарту). Прирост частоты кадров не измерен.

## Звук и Discord

С 0.7.7 при показе окна по умолчанию передаётся звук только этого окна (флажок «Звук только из этого окна»). Иначе (режим «Весь экран»)
передаётся весь звук компьютера **кроме Discord** (и Discord PTB/Canary, Vesktop) — поэтому друг не слышит
сам себя эхом, даже если вы сидите в голосовом канале. Если Discord запустить или перезапустить во время
трансляции — программа сама это заметит за пару секунд. Если Windows слишком старая и не умеет исключать
программы из захвата, а Discord запущен — звук не передаётся вообще (лучше тишина, чем эхо).
Проверить на своём ПК: `screenshare audiotest`.

Discord в браузере исключить нельзя (пришлось бы глушить весь браузер) — пользуйтесь приложением Discord.

## Если у показывающего нет NVENC (0.7.1)

Раньше при старом драйвере NVIDIA трансляция падала с «Function not implemented»: FFmpeg был собран под самый новый
NVENC API (13.1, драйвер от 610), а у друга (RTX 3060) стоял драйвер старше — `NvEncodeAPI` старого драйвера новый API
не понимает. Теперь:

- FFmpeg собран под **NVENC API 11.1** — нужен драйвер NVIDIA **471.41 (Windows) или новее**; всё, что выпущено после
  осени 2021, работает (RTX 3060 — любой нормальный драйвер).
- Если NVENC всё-таки не запустился (нет карты NVIDIA, драйвер старее 471.41, нет `nvEncodeAPI64.dll`), программа
  **сама переключается на кодирование процессором** (libx264, H.264) и пишет на странице «Показать мой экран» в статусе
  `Кодирование: процессор x264 ...` и красным причину: «Драйвер NVIDIA слишком старый ... нужен NVENC API 11.1, в драйвере
  X.Y; минимальная версия драйвера — 471.41».
- Процессорное кодирование ограничено по мощности: ≈ 1080p30 на 6+ ядрах (1080p60 на 12+, 720p30 на слабых), битрейт
  подстраивается под CPU. Картинка при этом масштабируется на стороне показывающего.
- Смотрящему ничего настраивать не надо: кодек (HEVC или H.264) определяется по первому ключевому кадру. **Нужна версия
  0.7.1 у обоих.**
- Строка статуса теперь начинается с кодировщика: `NVENC · 60 кадров/с ...` или `x264 (процессор) · 30 кадров/с ...`.
- Для проверки: переменная окружения `SS_ENCODER=x264` принудительно включает процессорный режим, `SS_ENCODER=nvenc`
  — только NVENC (без запасного).

FFmpeg теперь **GPL** (в нём статически слинкован x264); `third_party/ffmpeg/LICENSE.txt` — GPLv2. Собирается скриптом
`tools/build-ffmpeg.sh` (Linux, mingw-w64): FFmpeg n9.0.2 + nv-codec-headers n11.1.5.3 + x264.

## «Не удаётся продолжить выполнение кода, поскольку система не обнаружила avcodec-63.dll» (0.7.3)

Версии 0.7.1 и 0.7.2 на чистой Windows **не запускались** с этой ошибкой: библиотеки FFmpeg были подключены к exe
обычным (статическим) импортом, и Windows искала `avcodec-63.dll` ещё до того, как программа успевала распаковать их
из самого себя. Причина — GNU-библиотеки импорта от mingw-сборки FFmpeg, для которых /DELAYLOAD игнорируется; плюс
`avformat-63.dll` не входила в комплект вовсе. В 0.7.3 библиотеки импорта MSVC-формата (`tools/make-import-libs.sh`),
FFmpeg грузится отложенно, как в 0.7.0; сборка проверяется `tools/check-dlls.sh`. **Если у вас 0.7.1/0.7.2 — просто
замените файл на 0.7.3.**

## Если звук трещит (0.7.2)

Что исправлено в программе (звук идёт «хост → сеть → зритель», трещать может любое звено):
- **Зритель (там, где слышно треск):** раньше при малейшей нехватке данных звук обрывался в тишину и стартовал заново
  «со щелчком», при переполнении старый звук выбрасывался со щелчком, буфер был жёстко 40–50 мс (для интернета мало),
  а потерянный пакет заменялся повтором с разрывом на стыке. Теперь: адаптивный буфер 40–100 мс (сам растёт после
  каждого сбоя и медленно уменьшается в спокойные минуты), плавная подстройка скорости под дрейф часов (ПИ-регулятор,
  до ±0,8%), ресемплер с окном Кайзера вместо линейной интерполяции, затухание/нарастание за 3 мс вместо обрыва и
  «заделка» потерь продолжением последнего периода звука с плавным возвратом в настоящий звук.
- **Хост (тот, чей звук идёт):** поток захвата теперь в MMCSS «Pro Audio» (его не вытеснит игра/кодировщик), буфер
  захвата 100 мс, а потерянные системой отсчёты (DATA_DISCONTINUITY) считаются и сглаживаются; счётчик виден в строке
  статистики хоста («пропуски в захвате звука»). Округление float→int16 вместо усечения.
- **Диагностика:** в `%LOCALAPPDATA%\screenshare\viewer.log` каждые 5 с строка «звук: буфер … мс (цель …) · опустошений
  +N · переполнений +N · тишины … мс · дрейф … ppm · вывод … Гц, колбэк до … кадр. · потерянных пакетов …».
  Если «опустошений» и «заглушено» почти ноль, а треск есть — виновата не сеть и не программа, а звуковая карта,
  драйвер или **разветвитель/наушники** (ниже).

Если всё равно трещит, проверьте по порядку:
1. **Разветвитель «гарнитура от телефона → наушники + микрофон».** Такой переходник (3,5 мм TRRS → два штекера)
   сам по себе даёт шум, треск и «пердение»: у него дешёвые контакты, а если штекер вставлен не в тот разъём или
   не до конца — слышен треск при малейшем движении кабеля. Проверка: втыкнуть наушники-вкладыши (или любые
   наушники) **напрямую** в разъём наушников/колонок ПК или в USB-звуковую карту — если треск исчез, дело в разветвителе.
   Правильно: зелёный штекер — в зелёный (наушники), розовый — в розовый (микрофон); на ноутбуке с одним
   комбинированным разъёмом нужен именно разветвитель «TRRS-гнездо → 2 штекера» нужной распиновки (CTIA), а не наоборот.
   Лучший вариант — USB-гарнитура или дешёвая USB-звуковая карта (~500 ₽) + обычные наушники: без аналоговых контактов.
2. **Частота устройства вывода 48 кГц.** Windows → Параметры → Звук → устройство → «Формат по умолчанию» →
   «24 бит, 48000 Гц (студийная запись)». Программа сама пересчитывает частоту, но при 44,1 кГц драйвер делает ещё
   одну пересэмплировку, и дешёвые драйверы тут иногда трещат.
3. Отключить «Улучшения звука»/пространственный звук (Windows Sonic, Dolby, Realtek-эффекты) на устройстве вывода.
4. Не использовать Bluetooth-наушники для проверки — у них свои разрывы и задержка.
5. Закрыть всё лишнее с высокой нагрузкой на процессор у зрителя, обновить драйвер звука (Realtek).

## Если интернет с потерями пакетов

С версии 0.5.1 потерянные пакеты не ломают картинку: зритель просит у хоста *только недостающие* пакеты
(NACK), хост досылает их из буфера последних кадров; запрос целого ключевого кадра — крайняя мера, с паузой
и нарастающей задержкой. Битрейт сам снижается, если потери остаются после дозапроса, и медленно растёт
обратно, когда канал чистый. В звук добавлена копия предыдущего пакета, дыры заполняются точной длины
(копия → затухающий повтор → тишина), поэтому звук не «рубится».

В строке состояния у зрителя теперь: `кадров/с · Мбит/с · пинг · потери сети % (докачано N, ключевых запросов K) ·
звук: восст. A, заглушено B`.

Проверить на плохой связи у себя: на стороне, которая показывает экран, перед запуском задать
`set SS_SIM_LOSS=0.05` (доля выбрасываемых исходящих пакетов; по умолчанию выключено), необязательно ещё
`set SS_SIM_BURST=4` (потери пачками в среднем по 4 пакета). Симулятор без сети: `tools/lossim`
(`cargo run --release -- table`, результаты в `tools/lossim/RESULTS.md`).

Совместимость: новый зритель играет звук и от старого хоста (формат 0x91). А вот старый зритель не понимает новый
формат звука (0x92) — с новым хостом он покажет картинку, но без звука. Поэтому обновляйте **обоих**.

## Сборка

Нужны Rust, Visual Studio Build Tools (C++), LLVM, и FFmpeg shared-сборка
(собирается `tools/build-ffmpeg.sh`; готовая сборка с NVENC API 11.1 + x264 лежит в `third_party/ffmpeg`).
Библиотеки импорта FFmpeg должны быть в формате MSVC (иначе /DELAYLOAD не работает, см. 0.7.3). Один раз после новой
сборки FFmpeg: на Windows `powershell -ExecutionPolicy Bypass -File tools\make-import-libs.ps1`, на Linux
`tools/make-import-libs.sh`. Потом сборка и проверка зависимостей:

```
# статическая библиотека C (/MT): иначе exe требует VCRUNTIME140.dll, которой нет на чистой Windows; на Linux тот же флаг для cargo xwin
RUSTFLAGS="-C target-feature=+crt-static" cargo build --release
tools/check-dlls.sh      # Linux/WSL/git-bash: упадёт, если exe или DLL требуют чего-то, чего нет на чистой Windows
```

Установщик драйвера ViGEmBus (`vendor/vigembus/*.exe`, 6,3 МБ) тоже лежит в репозитории и встраивается в exe (`include_bytes!`); `build.rs` сверяет его sha256.
DLL FFmpeg встраиваются в exe (build.rs, zstd), грузятся отложенно и распаковываются при первом запуске
(src/bundle.rs) — на выходе один `target\release\screenshare.exe`.
